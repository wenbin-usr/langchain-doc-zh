开放式生成式 UI

在生成式 UI 频谱的开放端，渲染应用之外创建的 UI，例如沙盒化的 MCP Apps
约 2 分钟 社区翻译 查看英文原文 ↗

概览#

开放式生成式 UI 位于 生成式 UI 频谱 的智能体创建端。界面在你的应用之外编写，例如由 MCP 服务器生成，然后由你的前端在沙盒中渲染。你和智能体都不编写组件：组件由第三方交付，你的应用只负责承载它们。

这种方式提供了最宽的表达范围：智能体掌控画布。一项能力可以自带已构建好的界面，因此你可以呈现自己从未实现的交互式工具，而无需编写任何前端代码。它适用于一次性的可视化和定制化回答，在这类场景中，一个出人意料且足够好的结果胜过一个可预测的结果。它也是最实验性的方式，确定性最低、运行更慢且成本更高；不受信任的 UI 最难做到一致性、可访问性和安全性，因此必须与应用的其他部分隔离。

何时使用这种方式#

当你希望呈现位于应用之外、并独立于应用演进的能力和界面时，例如由 MCP 服务器生态发布的工具，就应选用开放式生成式 UI。当需要保证品牌、可访问性或布局时，应沿频谱回退到 声明式 或 受控 生成式 UI，此时组件由你的应用掌控。

MCP Apps#

模型上下文协议让智能体连接提供工具和资源的外部服务器。MCP Apps 将这一理念扩展到界面：MCP 服务器交付交互式 UI，前端通常以 iframe 的形式直接在对话中渲染它。服务器拥有组件、数据和交互，而你的应用负责提供外框和与智能体的连接。

CopilotKit 将这一模式记录为 MCP Apps。

沙盒与安全#

由于界面来自第三方，应将其视为不受信任的内容。在隔离的上下文中渲染它，例如沙盒化的 iframe，并限制它可访问的范围，使行为异常或恶意的应用无法触及页面的其他部分或用户的数据。沙盒化正是让频谱的开放端可用于生产的原因：它容纳了表达范围，而非限制表达范围。
