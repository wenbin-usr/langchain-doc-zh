多智能体

多智能体系统会协调专门化组件来处理复杂工作流。然而，并非每个复杂任务都需要这种方法——一个配备合适（有时是动态的）工具和提示词的单一智能体通常也能取得类似结果。

提示

如需内置的多智能体支持，请使用 Managed Deep Agents：这是一个基于 LangChain 构建的托管式高层运行框架，自带 子智能体、技能、规划、虚拟文件系统和上下文管理。或者，若要在使用同一 Deep Agents 运行框架的同时获得最大灵活性，可以使用 Deep Agents 自行托管智能体，或运行自定义的 LangSmith Deployment。

为什么需要多智能体？#

当开发者说需要“多智能体”时，他们通常是在寻求以下一项或多项能力：

  • 上下文管理：在不超出模型上下文窗口的前提下提供专门知识。如果上下文无限大且延迟为零，你可以把所有知识都塞进一个提示词——但现实并非如此，因此你需要一些模式来有选择地呈现相关信息。

  • 分布式开发：让不同团队独立开发和维护各项能力，并以清晰的边界将它们组合成更大的系统。

  • 并行化：为子任务派生专门的工作单元并并发执行，以更快获得结果。

当单个智能体拥有过多 工具 而难以正确选择时，当任务需要大量上下文支撑的专门知识（长提示词和领域专用工具）时，或者当你需要施加顺序约束、只有在满足特定条件后才解锁某些能力时，多智能体模式尤其有价值。

提示

多智能体设计的核心是 上下文工程——决定每个智能体看到哪些信息。系统的质量取决于能否确保每个智能体都能获取完成其任务所需的正确数据。

模式#

以下是构建多智能体系统的主要模式，各自适用于不同的用例：

模式工作方式
子智能体主智能体将子智能体作为工具进行协调。所有路由都经过主智能体，由它决定何时以及如何调用每个子智能体。
交接行为会根据状态动态变化。工具调用会更新状态变量，从而触发路由或配置变化，切换智能体，或调整当前智能体的工具和提示词。
技能按需加载专门的提示词和知识。单个智能体始终保持控制权，并根据需要从技能中加载上下文。
路由器路由步骤对输入进行分类，并将其导向一个或多个专门智能体。结果会被综合成一份合并的响应。
自定义工作流使用 LangGraph 构建定制的执行流程，混合确定性逻辑与智能体行为。可将其他模式作为节点嵌入你的工作流。

提示

你可以混合使用这些模式！例如，子智能体 架构可以调用工具，而这些工具又能调用自定义工作流或路由器智能体。子智能体甚至可以使用 技能 模式按需加载上下文。可能性无穷无尽！

可视化概览#

主智能体将子智能体作为工具进行协调。所有路由都经过主智能体。

智能体通过工具调用相互转移控制权。每个智能体都可以交接给其他智能体，或直接回复用户。

单个智能体按需加载专门的提示词和知识，同时始终保持控制权。

路由步骤对输入进行分类，并将其导向专门智能体。结果会被综合。

提示

使用 LangSmith 追踪跨智能体的完整协调流程。按 追踪快速入门 完成设置。

我们还建议你配置 LangSmith Engine，它会监控你的追踪记录、检测问题并提出修复建议。

性能对比#

不同模式具有不同的性能特征。理解这些权衡有助于你根据延迟和成本要求选择合适的模式。

关键指标：

  • 模型调用次数：LLM 的调用次数。调用越多，延迟越高（尤其是串行调用），单次请求的 API 成本也越高。

  • 处理的 token 数：所有调用中 上下文窗口 的总使用量。token 越多，处理成本越高，也越有可能触及上下文上限。

重复请求#

第 1 轮：“买咖啡” 第 2 轮：“再买一次咖啡”

用户在同一对话中重复相同的请求。

模式第 2 轮调用次数总计（两轮）最适用场景
子智能体48
交接25✅
技能25✅
路由器36

再次 4 次调用 → 共 8 次

  • 子智能体在设计上是 无状态的——每次调用都走相同的流程

  • 主智能体维护对话上下文，但子智能体每次都从头开始

  • 这提供了强上下文隔离，但会重复完整流程

2 次调用 → 共 5 次

  • 咖啡智能体从第 1 轮起 仍处于活动状态（状态持续存在）

  • 无需交接——智能体直接调用 buy_coffee 工具（第 1 次调用）

  • 智能体响应用户（第 2 次调用）

  • 跳过交接节省 1 次调用

2 次调用 → 共 5 次

  • 技能上下文在对话历史中已经加载

  • 无需重新加载——智能体直接调用 buy_coffee 工具（第 1 次调用）

  • 智能体响应用户（第 2 次调用）

  • 复用已加载的技能节省 1 次调用

再次 3 次调用 → 共 6 次

  • 路由器是无状态的——每次请求都需要一次 LLM 路由调用

  • 第 2 轮：路由器 LLM 调用（1）→ Milk 智能体调用 buy_coffee（2）→ Milk 智能体响应（3）

  • 可以通过将其包装为有状态智能体中的工具来优化

关键洞察： 有状态模式（交接、技能）在重复请求中可节省 40-50% 的调用。子智能体对每个请求保持稳定的成本——这种无状态设计提供了强大的上下文隔离，但代价是重复的模型调用。

多领域#

用户： "比较 Python、JavaScript 和 Rust 在 Web 开发中的表现"

每个语言智能体/技能包含约 2000 个 token 的文档。所有模式都可以发起并行工具调用。

模式模型调用次数总 token 数最适合
子智能体5~9K✅
交接7+~14K+
技能3~15K
路由器5~9K✅

5 次调用，约 9K token

每个子智能体都在隔离环境中工作，只持有相关上下文。总计：9K token。

7+ 次调用，约 14K+ token

交接串行执行——无法并行研究三种语言。不断增长的对话历史会增加开销。总计：约 14K+ token。

3 次调用，约 15K token

加载后，后续每次调用都会处理全部 6K token 的技能文档。由于上下文隔离，子智能体整体处理的 token 少 67%。总计：15K token。

5 次调用，约 9K token

路由器使用LLM 进行路由，然后并行调用各智能体。与子智能体类似，但多了一个显式路由步骤。总计：9K token。

关键洞察： 对于多领域任务，具备并行执行能力的模式（子智能体、路由器）最为高效。技能模式的调用次数更少，但由于上下文累积，token 用量很高。交接模式在此效率低下——它必须串行执行，无法利用并行工具调用来同时咨询多个领域。
